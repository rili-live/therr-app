## Location-based bot posts (therr-app + therr-ai-automator)

Goal: bot posts read as stilted because nothing about them is anchored anywhere.
Give some bots a home city, have them write about it, and put those posts in a
new user's feed once they share their location.

Both repos on `claude/location-based-bot-posts-4xx8hb` (therr-app's branch is
`general` + VERSIONS.txt, so the backend/shared work is landable).

therr-app:
- `20260821000001_main.thoughts.location.js` — latitude/longitude/locality,
  nullable, partial btree index on (latitude, longitude) WHERE NOT NULL.
- `ThoughtsStore.getRecentThoughts` takes an optional `nearLocation`: bounding
  box (indexable) + ST_DWithin (exact), distance aliased into the score so a
  geo-weighted profile can rank by it. PostGIS is already enabled in the users
  DB (20230815184654_main.users.js).
- content-ranking profiles gained `localMatchBoost` + `localFeedRadiusMeters`
  (env-tunable). PULSE 1.4 / 60km — the boost is applied at activation, never in
  SQL, so PULSE's emitted expression stays byte-identical.
- Distributor runs a third candidate query for the reaction owner's home point;
  `UserLocationsStore.getPrimary` accepts a first ping (getDwellings needs 3
  distinct days, which a new account can never have) with a 30-day recency guard.
- `createUserLocations` re-seeds the stream, gated on the shared distributor
  window (rows are keyed on ~111m-rounded coords, so pings are continuous).
- Seed `006_local_bot_users.js`: 12 metro bots + declared-home userLocations.

therr-ai-automator: `config/locales.ts` (12 metros, colour incl. everyday
gripes), joined to bot homes **by proximity, not by key**; LOCAL_THOUGHT_CHANCE
0.4; only local posts get coordinates, written as a complete pair or not at all.

Bug caught by a test I wrote for it: `Number(null)` is 0, so a userLocations row
with null coordinates resolved to Null Island and ran a local query against it.

## Follow-up: city detection on human posts

Zack asked whether human posts could inherit the author's home city. Talked him
off it (it would put someone's movie takes in front of their neighbors and
publish a guess about where they live on every post) and he pivoted to parsing
explicit city mentions, which keeps the column's meaning identical for humans
and bots: the coordinates are the post's SUBJECT, not the author's position.

The catalog already existed — `constants/Cities.ts`, 55 US cities with lat/lng
and a CityNameMap, already driving the SEO city pages. Reused it; added Miami
(a genuine gap in a top-US list, and the seeded Miami bot had no human-side
counterpart). New `location/detect-locality.ts` + wired into ThoughtsStore.create.

Precision decisions, all tested: names that double as people or ordinary words
(Austin/Phoenix/Charlotte/Mesa/Washington…) need a place cue or a state
qualifier; abbreviations match case-SENSITIVELY because "la" is a Spanish
article and we serve an es locale; two cities named = no tag (a journey, not a
place); "New Orleans, LA" consumes the state token so it isn't read as LA.

Refused to accept coordinates from the request body — createThought spreads
req.body, so that would let any client drop a post into any city's feed.

Second bug caught by a test written for it: the write-side gate didn't mirror
the read-side candidate filter (mature content). Now both are exactly
public + not mature + top-level.

Then Zack asked for a proximity gate: only tag when the author actually lives
near the city named, else null. Named the trade (loses the informed outsider /
visitor post) and built it — it closes a hole I had flagged and left open,
since post text is user-controlled and "Chicago" in every post would otherwise
farm that feed. Distance is checked against getPrimary, the SAME point the feed
uses, so the rule is symmetrical: you can only tag a city whose local feed you
would be served. 60km, matching PULSE's localFeedRadiusMeters.

ThoughtsStore.create is now async and takes an optional UserLocationsStore. No
locations store wired = tag nothing (fail closed); lookup throws = post still
saves untagged. Bots bypass all of this (direct DB writes).

## Open threads (new)
- Nothing renders `locality` in any client yet — the column is written and
  ranked on but never shown ("posted from Chicago" would close the loop).
- Local candidates only reach users whose home is within 60km of a catalog city.
- Bare adjectival use of an ambiguous name ("Austin traffic is insane") goes
  untagged. Now that the author's location is resolved in create anyway, a
  home-city tiebreak could recover these for free.
- A user with two homes (snowbird) can only tag near their primary location;
  getDwellings would cover it at the cost of a wider read.
- Portland always resolves to OR; ME is not in the catalog. Same shape of
  problem for any future duplicate name (Columbus, Springfield).
- WANDER is still unreleased and now for a different reason (few rows carry
  coordinates, not zero) — comments updated in algorithms.ts and its tests.
