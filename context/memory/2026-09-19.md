# 2026-09-19

## Goal

User got an admin email that a business claimed a space, but /dashboard-admin showed a
long list of unrelated "pending requests" and not the new claim. Root-cause or provide a
prod debug script.

## Findings (all confirmed, not inferred)

Four separate defects in the claim path, on `general` (branch
`claude/admin-dashboard-missing-claim-18rvdy`):

1. `claimSpace` (POST /spaces/request-claim/:spaceId — mobile "claim this space")
   called `updateSpace` without `fromUserId`. `updateSpace` puts `fromUserId` in its
   WHERE as an ownership check, so knex threw "Undefined binding(s)"; the handler's
   catch swallowed it and still returned 200. **Those claims were never written to the
   DB at all** — they exist only as the admin email. Verified against knex 3.3.
2. `SpacesStore.searchSpaces` ORed `isPublic = true` into the `isClaimPending` filter,
   then ordered by distance from Austin LIMIT 50 → the admin list was "the 50 public
   spaces nearest Austin". Explains both the misidentified rows and the missing claim.
3. `approveSpaceRequest` cleared the pending flag but never moved `fromUserId` to the
   claimant, and `updateSpace` silently drops `fromUserId` from its SET anyway. So
   `searchMySpaces` (keys on `fromUserId`) showed approved businesses nothing.
4. The non-super-admin guard in `searchSpaces` returned a plain object without touching
   `res` → hung the request.

Plus: sightengine re-flag scoped to `userId` not the row owner; ViewSpace read
`requestedByUserId` as "pending", pinning the banner to approved spaces.

## Decisions

- A claim on an **existing** space deliberately does NOT set `isClaimPending` — that
  would pull a live business off the map during review. The admin queue predicate is
  `isClaimPending = true OR (requestedByUserId IS NOT NULL AND fromUserId <> requestedByUserId)`,
  and approval transferring ownership is what clears shape 2 out of the queue.
- Ownership transfer lives in a new `SpacesStore.approveClaim`, deliberately NOT in
  `updateSpace` — letting that method write `fromUserId` would let a caller reassign the
  column that guards it.

- **Per-habit notification switches**: 4 NOT NULL DEFAULT true columns on
  `habits.user_habits` (reminders / streakAlerts / partnerActivity / pactUpdates),
  partial-write endpoint, gated at every producer (digest reminder pass + pact loop,
  partnerMissedDay/partnerCheckedIn on the recipient's switch, pactExpiring/pactEnded,
  streak sends on check-in). `pactNudge` deliberately excluded — a person poking you is
  a message, not an automated reminder.

  user kept that reminder) but contributes **no streak** to it — otherwise the
  loss-aversion framing returns through the copy and earns the evening last-chance push.
  `effectiveStreak()` in checkinNudgeRollup is the single place that decides it.
