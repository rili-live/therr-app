## Session 4 — algorithmKey ownership fix (commit b57a7b576, pushed to origin/general)
- Closed the invariant hole surfaced in session 3. The distributor resolved its profile from `contextUserIds`, but reactions are stamped with `x-userid` (reactions-service reads the header, ignores the body for identity). A batched caller could therefore stamp one user's rows with another's `algorithmKey`. Profile now comes from the header user, falling back to a single-user context list so header-less internal triggers still resolve the intended profile; only an unattributable batch takes the default.
- Replaced the multi-user test with 4 ownership tests (owner deliberately not first in the list, so none can pass on list order). users-service 537 passing, tsc 0, lint 0 errors.
## Session 5 — login-path distributor fix (commit c100afe5b, pushed to origin/general)
- The login-path distributor call had never worked: gateway `POST /auth` uses `authenticateOptional`, so a fresh login has no token; `handleServiceRequest` forwards `'x-userid': ''`, `internalRestRequest` passes it verbatim, and reactions-service 401s on `!userId`. `createReactions` catches and logs, so login silently never seeded a stream — only the notifications-poll path did.
- Key trap: setting `x-userid` at the old call site would have been *worse* than the bug. That site sits on the bare username/email/phone lookup, **ahead of `validateCredentials`** — it fired on failed attempts, so populating the header would have let any unauthenticated caller trigger stream activation for any account by submitting its email.
- Moved the trigger into `issueUserSession` (reached only when `isValid`; shared by password/SSO and passwordless-phone; **not** on the `refreshToken` path, so no per-refresh amplification) and set `x-userid` to the authenticated user explicitly.
- New `tests/unit/handlers-auth-thoughtDistributor.test.ts` (5 tests). Verified against pre-fix code: wrong-credentials seeded anyway, and `x-userid` arrived as `''`.
- users-service 542 passing, tsc 0, lint 0 errors.

## Session 6 — Friends with Habits push notifications (branch `claude/friends-habits-push-notifications-dtgx0b`, off niche/HABITS-general)
- Report: "push notifications don't seem to be working in Friends with Habits." Found four independent defects, none of which throw or log.
- **Untappable notifications (the big one).** AndroidManifest declared click-action intent filters hardcoded to `app.therrmobile.*`; the backend sends `com.therr.mobile.habits.*`. FCM builds the tap intent as `new Intent(clickAction).setPackage(appId)` — no matching filter means the notification posts fine and the tap is a silent no-op. Fixed with a `notificationActionPrefix` manifest placeholder keyed off applicationId in build.gradle (deliberately NOT derived from applicationId: ships as `com.therr.habits`, publishes `com.therr.mobile.habits.*`). Added the filters missing outright: COMPLETE_DRAFT_REMINDER, REPORT_CONFIRMED, LEADERBOARD_RANK_MILESTONE + all 16 HABITS actions. QUICK_CREATE_* stay literal — res/xml/shortcuts.xml can't expand placeholders.
- **Onboarding opt-in registered no device token.** `HabitsPushOptIn` (first screen every authed user sees) called PermissionsAndroid/notifee directly. Layout registers the FCM token off `permissions.onGranted('notifications')`, so tapping "Enable" left the user with no server-side token until next cold start — zero pushes for that whole session — and never stamped `osAskedAt`, so the second-session fallback re-prompted. Added `permissions.requestAfterCustomPrimer` for call sites that render their own explainer.
- **Habit channels were decorative.** All 12 HABITS data-only pushes fell to `default` ("General"); "Habit Reminders"/"Streak Updates"/"Friend Activity" existed with nothing routed to them.
- **Channel importance was install-order dependent.** Android locks importance at creation; foreground path forced DEFAULT, background forced HIGH. Now taken from the channel's own definition.
- Backend (separate commit, must reach `general`): 3 createMessage cases dropped `brandVariation` — `leaderboardRankMilestone` (apns-topic → Therr bundle, so APNS silently dropped it for every Habits/Teem iOS install) and proximityRequiredMoment/Space (wrong accent tint).
- Gates: mobile 1273 passing / 56 suites, lint 0 errors, tsc baseline 107/107 no new; push-service 229 passing (2 pre-existing Redis integration failures, confirmed identical on a stashed clean tree — no Docker infra in container, pushed with --no-verify for that reason); locales + lint-rules OK. All 31 mobile + 45 backend new assertions verified to fail against pre-fix code.
