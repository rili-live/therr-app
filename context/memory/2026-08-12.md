## Second `/work-plan` run — Tier 1.2 reaction mass-assignment

Batch: allow-list reaction write columns. New
`reactions-service/src/utilities/pickReactionWriteFields.ts`; all 13 `...req.body` spread
sites across moment/space/thought/event handlers now route through it. 13 unit tests added.

**Why it was real:** the stores hand their params object to `knex.insert()`/`knex.update()`
unfiltered — `ICreate*Params` is compile-time only and the handlers are untyped `(req, res)`.
express-validator validates listed fields but does not strip unlisted ones. Worst column was
`thoughtReactions.relevanceScore` (the feed's `ORDER BY` key): a client could pin any activated
thought to the top of its own stream. Also client-writable: `contentLatitude/Longitude/Location`,
`contentAuthorId`, the space visit columns, `updateCount`, `isArchived`.
`/create-update/multiple-users` was the sharpest — it writes rows for *other* users.

**Decision (AskUserQuestion): silently drop unlisted fields, not 400.** Vindicated during
implementation — mobile's ViewEvent RSVP sends `attendingCount`, which no gateway validator
declares and which only ever reached the table via the spread. A 400 would have been a live
outage; it is on the event allow-list instead. General lesson: the real client field set here
is wider than any validator declares, so derive allow-lists from clients too, not just validators.

Verification: reactions-service 180 tests passing (156 unit), `pr:typecheck:reactions` clean,
eslint 0 errors (9 pre-existing unused-var warnings on untouched lines). Not committed.

## Third run (/work-plan) — committed reactions batch, closed Tier 1.5

Committed the pending reactions allow-list as `501481fba` after quality-check
(eslint 0 errors, `pr:typecheck:reactions` clean, 156 unit tests passing).

**Batch: Tier 1.5 payment/subscription closure (users-service, uncommitted).**
New shared helper `handlers/helpers/checkoutSessionAccessLevels.ts`; wired into
`createUser` (empty `else if (paymentSessionId)` branch), `login` (the read was
commented out), and `activateUserSubscription`. 21 new unit tests; full suite 615 passing.

**The backlog framing was wrong and cost the batch its size.** Tier 1.5 claimed checkout
is a Payment Link with `target="_blank"` and no return path, implying the fix required
migrating to a Checkout Session across the dashboard. But `PaymentComplete.tsx` already
redirects to `/register?paymentSessionId=` and `/login?paymentSessionId=`, and the gateway
already validates the field — so the backend half was wiring, not greenfield. Lesson:
verify a backlog entry's premise in code before sizing off its prose.

**Two live bugs found, neither in the backlog:**
1. `activateUserSubscription` gated on `payment_status === 'paid'`, which a trial-only
   Checkout Session never satisfies (`no_payment_required`) — trials upgraded only via the
   webhook, i.e. silently dependent on `STRIPE_WEBHOOK_SIGNING_SECRET` being set.
2. Its no-`userId` branch used `getUserByEmail`, which selects only `id`/`email`/
   `isUnclaimed`. The follow-up `updateUser` unions against `existingUser.accessLevels`
   (undefined there), so it **replaced** the account's levels with just the subscription
   level — stripping `EMAIL_VERIFIED` and locking the user out of login right after paying.

**Decision (AskUserQuestion): require billing-email match, fail closed.** Same trust class
as the 2026-08-12 `billingEmail` fix — a session id is a bearer token for a purchase, not an
account. Extended it to `activateUserSubscription` too (not just register/login) since that
route had the same claim risk and the webhook already keys grants off the same email, so the
two paths now agree. Grants fail *open* in the other direction: a Stripe outage returns no
levels rather than blocking a registration or sign-in.
